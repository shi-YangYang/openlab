# spec-023 实验自动执行决策

## 决策标题

确定「实验自动执行」的模式（人工/Agent 主导双轨）、执行过程呈现方式与失败兜底策略。

## 元信息

- **日期**：2026-08-27
- **状态**：accepted
- **决策者**：用户
- **关联 Spec**：spec-023-experiment-execution

## 背景与问题

Phase 5 的最后一环——「实验自动执行与结果回传」（spec-008 划出、留待后续）尚未落地。实验方案（spec-007，含 hypothesis/goal/datasets/baselines/metrics 结构化字段）、服务器管理/部署/命令执行/监控（spec-008/009）、Web 终端与 Agent 审批机制均已就绪，具备闭环条件。

## 备选方案

- 方案 A：纯结构化流程页 —— 表单化选服务器/方案→固定流水线执行。可控但僵硬，环境差异处理弱。
- 方案 B：纯 Agent 主导 —— 一句话让 Agent 全自动跑完。灵活但黑盒，人工难介入。
- 方案 C：双轨结合（采用）。

## 决策

1. **双轨模式**：
   - **人工主导模式**：新增「执行」面板承载结构化流程——选择服务器 + 选择实验方案（可附带历史创新点上下文），按步骤推进：`同步代码（clone/SFTP 二选一）→ 环境准备 → 启动训练 → 查看输出`。每一步都由用户点击触发、确认命令后执行，输出实时回显；任何一步都可以跳过或改成自定义命令。
   - **Agent 主导模式**：Agent 新增 `run_experiment` 工具（入参 experiment_id + server_id），工具内部把结构化方案渲染为一份执行计划交给既有 agent 循环自主编排（复用 run_command/deploy_code 等既有工具，危险操作照常走审批）。用户一句话即可发起，也可中途用「停止」打断。
2. **结果呈现**：不做独立的指标解析回传。以**运行日志为核心**——执行的每条命令的 stdout/stderr 实时流式展示在「执行」面板（步骤式时间线）；Web 终端始终可随时切入人工排查；任务结束把完整日志与会话记录持久化为该次运行的执行报告。
3. **失败兜底**：任一步骤失败先自动重试 1 次（幂等类操作如安装/下载）；再失败则暂停整条流水线并标记失败点，交由人工接管——可在面板上改命令重试该步、跳过、或切换到 Web 终端手工处理后继续。

## 理由

- 双轨让「想省事的人」一句话全自动，「想掌控的人」每步点确认，且两种模式共享同一套底层命令执行通道，不重复造轮子。
- 训练任务的产出主要是日志形态的指标输出，ML 场景下 loss/accuracy 天然在 stdout 里；引入结构化指标抽取反而脆弱，日志+终端已足够，后续有真实需求再加指标解析。
- 「重试一次→暂停等人」符合 GPU 长任务现实：盲目多次重试浪费卡时，彻底停下又太脆。

## 影响与后果

- 后端新增 experiment run 执行器（步骤状态机）与日志流式推送（复用 WebSocket 心智）；agent 工具表新增 run_experiment。
- 前端实验方案历史页增加「执行」入口与新执行面板组件。
- 远程进程生命周期：启动训练后需要记录 PID 并支持停止（防止脱离控制的后台进程长期占卡）。
